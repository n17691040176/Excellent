## 修复结果

| 原问题 | 当前行为 |
| --- | --- |
| 普通订单获取席位、同一订单重复获取不同城市 | 新增专用席位订单，绑定席位、报价与版本；购买元数据以订单 ID 为主键，重复回调不重复分配或入账。 |
| 退款后继续持有席位和奖励 | 成功分配席位后禁止普通退款，且在调用渠道退款前校验；正在渠道退款的订单不能再领取席位。历史成功轮换也受退款保护。 |
| 新模式重复支付旧区域代理奖励 | 按订单锁定模式隔离，CITY_PARTNER 不再触发旧区域奖励。 |
| 公司、运维分配未入账 | 实际记入对应内部账户；按固定顺序加锁，尾差归公司，确保支付金额与分配总额一致。 |
| 保存规则后读取默认值 | 返回真实规则字段，更新规则版本，前后台使用一致的字段。 |
| 缺少规则校验 | 服务端校验金额、层数、衰减比例及可分配利润；修改价格或成本时同样检查现有规则。非法 Decimal 参数返回 422。 |
| 公司剩余收益无法结算或取消 | 新流水绑定真实公司账户，参与冻结、结算、取消；历史空受益人流水可更新生命周期状态，但不自动补记余额。 |
| 新流水、模式与席位入口不完整 | 前后台展示新旧流水及角色；后台读取真实全局模式，支持席位管理；移动端支持席位列表、下单与支付。 |
| 0% 衰减被当成 50% | 保留显式零值；付款时保存商品规则、成本及售价快照。 |

同一报价可有多个待付款买家，但并发付款只允许一笔取得席位。另一笔保留真实已付款状态和未履约原因，允许退款，避免将已收款误报成支付失败。成功席位的特殊退款、奖励冲正和席位回退不属于普通商品退款流程，本次没有新增特殊退款功能。

## 数据库与账户

应用启动迁移支持新的 `CITY_PARTNER_ORDER` 类型，并创建 `city_partner_purchases` 表。公司与运维账户为禁止登录的内部账户，保留已有余额；`users.system_account_type` 增加唯一约束，普通用户的 NULL 不受影响。发现重复内部账户时明确报错，不自动合并资金。

手动迁移参考 `server/sql/20260910_city_partner_purchase.sql`。该脚本用于尚未完成对应迁移的数据库，唯一索引语句不应在应用已创建该索引后重复执行。本次只验证了本地测试库，没有执行生产迁移。
