## 三个专项失败

1. **切换前城市配置校验缺失（§4.3）。** 有有效商品规则和内部账户、但没有任何城市席位配置时，切换到 CITY_PARTNER 仍成功。实现只校验内部账户和已启用商品规则，未检查城市及退款配置，也未提供完整的配置就绪结果。位置：`server/app/services/commission_service.py:720`。可能后果是管理员在城市配置未准备好时启用新模式，城市份额按缺位规则进入公司。

   这里需要区分文档与验收解释：文档明确要求校验“城市配置”，但没有定义何为就绪。本用例采用“至少已配置一个城市席位”的验收解释；§6.4 同时允许具体订单城市没有合伙人，因此不能推导出“所有城市必须有人持有”。如业务允许零席位启动，应明确这个条件，并在切换前展示检查结果和资金去向，而不是仅靠本用例决定业务规则。

2. **后台缺少最近切换信息（§10.1）。** 切换日志已写数据库，但重新读取模式接口没有 `reason`；浏览器页面也没有展示生效时间、最近切换人和原因。接口虽然返回 `updated_by`、`updated_at`，页面未展示，且它们来自配置行，不是完整的最近切换记录。位置：`server/app/services/commission_service.py:690`、`admin-web/src/views/commission/CommissionView.vue:22`。这是查询与展示缺口，不是“切换日志没有保存”。

3. **分润流水没有保留取整前原始金额（§9.2）。** 例子第七层理论金额为 3.125，实际发放应为 3.12；当前 `calculated_amount` 也存成 3.12，而且数据库字段只有两位小数。实际发放和公司 3.13 尾差正确，但无法从原始金额字段核对丢弃的小数。位置：`server/app/services/commission_service.py:849`、`server/app/models/city_partner.py:98`。

## 代码与页面核查补充缺口

这些项目通过源码/页面检查确认，不计入上面的三个运行失败数。

- **规则修改审计不完整（§12.10）。** 商品规则保存会生成新版本并覆盖当前配置，但没有保存每次修改的前后值、操作者和原因；没有订单引用的中间版本无法追溯。席位增长比例、上限、状态更新也没有对应的配置审计历史。位置：`catalog_service.py:1494`、`city_partner_service.py:101`。订单快照和模式切换日志不能替代所有规则修改的审计记录。
- **席位管理展示未覆盖 §10.2 全部字段。** 页面已有城市、持有人、购买报价、增长比例、成交次数及分配记录；现有席位的初始价格、任期时间未展示，历史记录未展示前后任用户及结算时间。席位接口没有返回当前购买订单 ID，模型中已有该字段。历史抽屉有订单号，因此并非完全没有购买记录。
- **异常结算人工处理能力有限（§11）。** 已有专用购买记录及 `settlement_error`，支持未履约退款；未发现对应的后台异常结算列表和人工处理入口。是否将退款路径视为本期人工处理方案，需要在验收范围中说明。
- **省市仍为自由文本。** 席位创建仅检查非空和同名唯一，后台可以输入任意省市名称；商品归属则按地址省市完全匹配。若名称不一致，将按无合伙人处理。文档要求沿用原省市标准，当前没有在席位管理端提供标准选择或名称校验。

## 文档本身未定，不能冒充已确认的规则

| 条款 | 当前行为 | 判定 |
| --- | --- | --- |
| §8.2、§14.6：售后释放周期 | 付款生成冻结流水；收货确认完成后立即释放，非物流订单付款即完成并释放，没有单独等待售后期。 | 与 §8.2 建议时序不同，但 §14 又将周期列为待确认。需要确定售后期限和完成后退款规则。 |
| §11、§14.7：席位退款 | 成功取得席位后拒绝普通退款，未履约已付款订单可退款；未新增特殊退款及完整席位冲正功能。 | 符合 §11 的普通退款建议，特殊退款尚不具备。 |
| §5.4、§14.8：达到上限后继续轮换 | 可按上限完成一次成交，随后停止轮换。0% 增长同样因下一次价格不增加而停止。 | “达到上限后是否继续”仍未确认，不能把停止轮换说成用户已定要求。 |
| §14.1–5、§14.9–10 | 按件；按地址省市；付款时成本快照；缺失上级/席位份额归公司；逐商品启用；同一用户可持有多个城市。 | 前五项符合文档默认值，逐商品启用及多城持有仍需形成最终规则。 |
| §3、§4.1：原模式下的席位交易 | 席位购买入口没有校验全局模式，专用席位订单固定为 CITY_PARTNER。 | 商品分润保持互斥；若“原模式城市合伙人不参与”也要求关闭席位买卖，当前仍存在边界缺口。 |

建议验收顺序：先补齐明确的展示、计算明细和规则审计，再明确配置就绪条件、售后释放、封顶轮换及原模式席位交易边界，最后按确认后的条件重跑专项验收。

## 复现与访问

在项目 `server` 目录执行文档专项：

```powershell
$env:PYTHONPATH = "$PWD;$PWD/tests"
python -m pytest ../tools/acceptance_city_partner.py -q --disable-warnings --tb=short --junitxml=../logs/local-test/document-acceptance.xml
```

此命令当前预期返回非零退出码，因为保留三个未满足的验收断言。它只使用隔离内存数据库；MySQL 并发验证属于单独的后端全量命令，通过 `CITY_PARTNER_MYSQL_TEST_URL` 显式指定本地 `_test` 库。

后台继续运行于 [佣金与席位管理](http://127.0.0.1:5173/commission)，移动端继续运行于 [城市合伙人](http://127.0.0.1:5174/#/subpackages/profile/city-partners)。浏览器证据：`logs/local-test/document-browser-results.json`、`document-ui.json`、`document-admin.png`、`document-mobile-seat-order.png`。

本次新增验收脚本和报告，未改变上述业务规则。支付、短信均为本地模拟；真实渠道付款、退款到账以及生产历史账务未验证。测试产生带测试标识的本地席位、订单和切换日志，保留供复核；历史异常余额未自动调整。
