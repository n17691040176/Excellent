# 新旧分润交错操作补测

日期：2026-09-10。延续本地城市合伙人分润验证，范围为多个请求交错修改模式、规则、席位及佣金状态。仍使用 Docker 项目 `excellent-localtest` 和模拟支付，不涉及生产数据。

## 本轮复现并修复的问题

| 场景 | 修复前的实测结果 | 修复 |
|---|---|---|
| 会话缓存 CITY_PARTNER，数据库已变成 ORIGINAL，再请求切回 CITY_PARTNER | 返回无需切换，数据库仍为 ORIGINAL | 模式切换锁定配置后刷新，按真实状态处理并记录审计 |
| 退款会话先缓存冻结流水，另一事务已将其释放 | 新、旧模式均可能按旧的 FROZEN 分支收回，遗漏已释放的可用余额 | 撤销先锁订单，读取流水时刷新状态，按最新 FROZEN/SETTLED 分支收回；释放也刷新所锁定的流水 |
| 席位页面读取报价 1200 后，报价被另一操作更新至 1440，管理员设置上限 1300 | 按缓存的 1200 校验，错误接受低于当前报价的上限 | 席位编辑锁定后刷新报价和版本再校验 |
| 新模式付款前已缓存商品成本、规则和城市持有人，随后这些数据被更新 | 付款可能使用旧成本 700、旧直推 400、旧持有人 | 付款时刷新并锁定成本、规则、持有人，再保存快照；商品按 ID 顺序锁定 |
| 原模式付款缓存成本 700、比例 12.5%，数据库已改为 800、20% | 仍按旧利润 900 计算 | 原模式同样刷新并锁定商品成本及专属规则；示例应以利润 800 发 160 |
| 后台抽屉打开后，另一管理员编辑另一套规则，再保存本套规则 | 抽屉将另一套规则覆盖回打开时的旧值 | 表单保留加载基准，只提交实际编辑的字段；后台已有字段合并逻辑继续保留并发修改 |

前五类问题使用固定时序的回归用例先复现失败，再完成修复；后台覆盖问题先在真实浏览器中复现。缓存用例刻意保留会话中的旧 ORM 对象，并不表示普通短请求每次都会触发。此前未覆盖这些交错时序，因此上一轮通过结果不足以排除这些问题。

同一字段被两位管理员修改，当前仍由后保存者覆盖先保存者；本次保护的是未编辑字段和另一套规则，没有引入全表单版本冲突确认机制。

## 新增验证及结果

本轮新增 11 个后端回归场景：6 个状态/缓存场景，5 个真实 MySQL 交错/并发场景。完整回归 **326 passed，2 subtests passed，1 warning**，包含共 9 项实际 MySQL 测试，无跳过。文档、边界和原版计算器对照 **53 passed**。后台 lint 通过，服务端和后台 Docker 构建通过。

新增 MySQL 验证使用独立数据库会话，覆盖：

1. 新、旧模式各一次：退款线程先读取冻结流水，结算线程随后完成释放，退款线程再收回，最终账户精确回到该订单入账前状态，保留其他订单余额。
2. 两个管理员同时读取旧商品规则，分别修改新直推金额和原固定金额，最终两项修改均保留。
3. ORIGINAL、CITY_PARTNER 两个方向：付款线程缓存切换前模式，切换线程完成切换，付款线程再处理付款，最终只生成切换后对应的一套流水。

这些是控制时序的事务正确性检查，不是吞吐量或长时间压力测试；模式切换测试均在结束时恢复原模式。

更新后的 Docker 后台浏览器验证已通过双向覆盖检查：

- 抽屉编辑新直推，外部请求将原固定奖改为 11，再保存抽屉，原奖仍为 11。
- 重新打开抽屉编辑原奖为 9，外部请求将新直推改为 350，再保存抽屉，新直推仍为 350。
- 四项手填、七层只读预览、接口拒绝篡改及超池、模式切换不改商品规则、同城唯一、自我接替拒绝、移动端自身席位按钮禁用继续通过。

最终浏览器记录未出现页面异常或非预期 HTTP 失败。测试保留带标识的本地商品、用户、席位和订单。

重建服务后还重新执行了完整异常交易恢复流程：待处理商品订单在后台与移动端可见、后台退款完成、移动端退款提示更新、普通用户不能访问管理接口、恢复报价的席位可由其他用户接替，全部通过。5 个 Docker 服务 healthy；9 个关键后端文件的 SHA-256 与工作区一致。

数据审计再次确认：混用商品流水订单、新模式出现原/区域流水、原模式出现新流水、重复城市席位、负佣金余额、冻结汇总不一致均为 0。此前本地测试的 2 条历史自我轮换记录继续保留。

证据：`logs/local-test/interleaved-regression.xml`、`interleaved-acceptance.xml`、`interleaved-data-audit.json`、`interleaved-container-hashes.json`，以及更新后的 `isolation-browser-results.json`、`recovery-browser-results.json` 和对应截图。回归脚本位于 `server/tests/test_commission_mode_isolation.py`、`server/tests/test_commission_isolation_mysql.py`；后台浏览器脚本为 `tools/isolation-browser.cjs`。

## 口径纠正与未覆盖范围

“历史订单不重算”应准确理解为：**已经生成的分润流水不因切模式或改规则而重算**。新模式在付款时生成完整规则快照。原模式的区域代理奖励保留旧行为：在订单完成时首次计算，读取那时的商品/代理配置；不能声称原体系所有奖励都已按付款时规则冻结。原版对照测试保持此行为，没有将原区域奖改造成付款快照机制。

七层关系、每市唯一和禁止自我接替的业务口径未变。真实支付渠道、生产历史全量对账、长时压力测试及特殊席位冲正不在本轮范围。前一报告中列出的售后释放时机和余额不足收回限制继续存在。
