**按实际业务复述**

1. 后台先配置公司、运维账户，城市席位和商品新规则，再切换全局商品分润模式。切换到新模式要求至少一个启用席位（可以无人持有）、至少一个启用且合法的商品规则，并检查全部启用规则。退款检查目前展示固定政策并通过，不是可配置的售后周期引擎。切换记录包含前后模式、管理员、时间、原因、未完成订单数和冻结金额。
2. 普通商品订单在支付成功处理时决定采用 ORIGINAL 还是 CITY_PARTNER。下单时间不是分界：切换前下单但切换后付款，会用付款时的模式。历史订单的释放与收回依据既有流水，不按最新模式重新算钱。
3. 原模式继续使用原商品专属规则或原分销规则；一般商品查找最多三层上级并检查原受益资格，复购走原直推规则，未采用专属规则的商品可走原团队奖励；市、区县代理仍走原区域收益。具体比例取原后台规则，不是新模式的固定 100/400/200。回归验证了原专属奖及市、区县代理收益，在模式切换后仍保留并可按原路径收回。
4. 新模式商品不走上述原分销和区域代理分润。是否参与新模式由每个商品配置；未启用的商品不产生新分润，也不会回退原分润。仍只有一个全局商品模式，并不是让不同商品同时选择两套模式。
5. 城市席位按省、市组合唯一。创建席位不等于已经有合伙人。购买者必须创建该席位的专用订单，订单绑定报价和价格版本；普通商品订单不能用来领席位，也不能一单领多个城市。
6. 首购价格 P：买家直接上级获 P×10%，公司获剩余 90%；无上级则公司获 100%。例如首次支付 1000 元，有上级时上级 100、公司 900。系统支付校验成功后自动确认，购买者成为当前合伙人，没有另一个人工确认按钮作为必经步骤。
7. 接替时以上任实际支付价为本金。若从 1000 涨至 1200，增值 200：上任本金 1000 加奖励 80，共 1080；公司 60；新买家上级 20；运维 40，合计 1200。无上级时该 20 归公司。各项分以下向下取整，剩余差额归公司。新旧持有人切换、账户入账和轮换流水同事务执行，重复确认不重复发钱。
8. 本金返还及奖励进入系统内的佣金可用余额。这里的“返还”并不是立即原路退回银行卡或微信；对外提现和实际到账是后续环节。公司与运维有独立内部账户，席位流水与商品流水分开保存，但个人汇总余额会合并其收益。
9. 当前价格字段表示下一位买家的报价。每次成功后，下一报价=本次成交价×(1+增长率)，有上限则取较小值。例如 1000、增长 20%，下一报价 1200。编辑增长率会使旧价格版本失效，但不立即重算已有报价；1200 报价改为增长 50%后，下一次仍付 1200，再下次才为 1800。
10. 达到上限成交一次后，不再允许同价轮换；0% 增长或向下取整后无涨价也会停止。允许一个用户持有多个城市；目前还允许现持有人再次购买自己的同一席位，轮换次数会增加。
11. 两个人可以针对同一报价付款，只有一个能取得席位。后到的付款仍记为已付，保留失败原因并进入后台未履约席位订单处理，可办理退款。并非限制只能有一人支付。未付款不会转移席位；有进行中的渠道退款时不能再取得席位；成功取得席位后禁止普通退款，特殊全量冲正尚未实现。
12. 新模式商品的单位分润池=订单明细单价−支付时商品成本，按件计算。单价在下单时保存；成本和规则在付款时读取，然后保存快照。积分/余额抵扣减少需外付现金，但不减少这里的商品售价。因此分润池并不等于本次外部现金到账减成本。
13. 支付冻结时按订单关联收货地址的省、市查找启用且有持有人的席位，并锁定当时的受益人。以后换合伙人、改地址、调规则或切模式，都不重算已经生成的流水。普通无需配送商品结账不保留收货地址，因此没有匹配城市，其城市份额归公司。

以文档售价 1600、成本 700、数量 1 且七层关系齐全为例：

| 分配角色 | 金额（元） |
|---|---:|
| 当前收货城市合伙人 | 100.00 |
| 直推奖 | 400.00 |
| 上级第 1 层 | 200.00 |
| 上级第 2 层 | 100.00 |
| 上级第 3 层 | 50.00 |
| 上级第 4 层 | 25.00 |
| 上级第 5 层 | 12.50 |
| 上级第 6 层 | 6.25 |
| 上级第 7 层 | 3.12 |
| 公司余款 | 3.13 |
| 合计 | 900.00 |

直推奖和上级第 1 层的受益人都是购买者的同一个直接上级，所以这个人合计获 600 元，而不是只获 400 元。公司余款既包含取整差额，也包含未分配利润和缺失受益人的份额；不仅仅是一分钱级别的尾差。没有城市合伙人时该 100 元归公司；缺少某层上级时该层金额归公司，不越级补发、不转给旧代理。城市和所有上级都没有时，900 元全归公司。运维账户不参与该商品分润，只参与席位接替的增值分配。

两件商品先分别按件取整再乘二：第七层 6.24、公司 6.26，总池 1800；不是先将第七层未取整的 3.125 乘二再发 6.25。当前算法保留理论原始金额，老流水不能恢复的精度标记为未知。

14. 配送商品付款即冻结，确认收货、完成订单即转入可用余额；无需配送商品付款即完成并释放，没有额外售后等待期。商品允许退款时，冻结流水取消、已结算流水扣回对应账户可用余额，不按当前规则重新计算。已完成配送订单当前普通退款入口拒绝；已完成的普通无需配送订单允许进入退款，但受益账户余额不足会使内部冲正失败。本地生活订单另走核销流程。不能把直接调用分润冲正服务的测试理解成所有已完成订单都能在前台退款。
15. 后台提供当前模式、切换记录、席位/历史轮换、规则/修改审计、商品新分润流水和未履约席位订单；移动端可查看席位、购买订单及新分润流水。席位配置与模式切换等写操作限制超级管理员。任期记录的是起始时间，目前没有文档规定的固定到期日，也未实现定期自动更换。

**确认的问题、差异及建议**

1. **优先修复：待付款调价能使外部支付确认失败。** 已通过实际后台商品更新服务和支付确认服务重现：旧订单 1600/成本 700；后台合法改为售价 2000/成本 1000，新商品池为 1000，规则可保存；旧订单付款仍用 1600，但成本读取 1000，池仅 600，原规则计划约 896.87，支付确认抛出超池异常。事务回滚后订单仍 UNPAID、支付流水仍 PENDING。代码事实已验证；“真实渠道已经收款而本地未记成功”是由该确认路径推导的风险，未进行真实渠道扣款复现。建议付款前校验待付订单兼容性，并将外部支付事实与分润失败待处理分开保存；不要为绕过错误而超发。
2. **功能缺口：停止轮换后没有恢复报价机制。** 1000 首购，封顶 1100 接替后，把上限调为 2000，仍报达到上限；0% 增长成交后再改 20% 同样无效。原因是编辑只改规则/版本，不重算当前报价，而再次成功购买才会重算，形成无法继续的状态。建议明确恢复策略，重算未来报价并使旧报价失效；这是建议，不是本轮已修复。
3. **模式作用范围不同。** 文档 §3 写原模式城市合伙人“不参与”，实际全局开关只控制商品分润，原模式下仍可购买、接替城市席位。若“不参与”只指商品收益，可解释为范围需写清；若要求整个城市合伙人业务停用，则当前不符合。
4. **释放时间和退款闭环不同。** §8.2 的售后期结束再释放未实现；已完成配送商品普通退款被禁止；特殊席位退款不存在。已释放余额可能已提现，当前不足余额会阻止冲正。真实渠道退款先发生、内部冲正失败时还需对账恢复策略；不能将“退款政策检查通过”当作这些能力已实现。
5. **递减取整顺序需定稿。** 当前是理论金额连续递减，每层独立向下取整；如果文档“上一层金额”指上一层已发金额，则不同。例如起始 200、33% 递减：第五层当前发 2.37，逐层取整递推应为 2.36。文档 200/50% 的七层示例两种算法相同，所以原示例测试不会暴露差异。
6. **自己接替自己未限制。** 已实测同一人可以对同城再次支付，记录新旧持有人相同，仍返还其旧本金并产生奖励和新报价。文档只待定“一人多城”，未说明这一行为。建议明确是否禁止以及关联账户接替规则；当前不能理解为每次轮换必然换人。
7. **“实际卖价”和资金到账需明确定义。** 800 抵扣+800 外付购买 1600 商品，仍按 1600−700=900 分配。抵扣若是足额已充值余额，和赠送积分对利润与现金流的含义不同，不能仅凭现金少就断言超发；应在文档明确抵扣资金来源与成本承担。900 池在受益人齐全时几乎全部分完，公司只留 3.13，还需说明 700 成本是否包含运费、税费、支付费和售后成本。
