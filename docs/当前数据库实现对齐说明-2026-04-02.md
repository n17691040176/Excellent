## 1. 当前数据库落地概况

### 1.1 当前真实落地范围
- 规划版数据库文档共设计 `38` 张表。
- 当前 `server/sql/schema.sql` 已落地 `34` 张表。
- 当前 `server/app/models/` 已落地 `34` 个对应 SQLAlchemy 模型。
- 当前运行时建表入口为 `server/app/db/init_db.py`，通过 `Base.metadata.create_all()` 以 ORM 模型为主执行初始化。
- 当前 `server/sql/schema.sql` 可作为 MySQL 手动初始化脚本使用，表覆盖范围与 ORM 模型保持一致。

### 1.2 当前实现结论
- 当前数据库已覆盖一期 APP 主链路：用户、团队、邀请返现、套餐、四大专区商品、资产体系、订单、地址、供应商招商、本地生活。
- 当前缺失的是少量“平台治理类 / 拆分精细化类”表，而不是核心交易链路表。
- 因此当前代码库更适合定义为“可运行的轻量一体化数据库实现”，不是“已百分百完成规划版所有表设计”。

## 3. 当前未落地的规划表

对比 `docs/数据库设计-校对版.md`，当前尚未在 `server/sql/schema.sql` 和 `server/app/models/` 中落地的表共 `4` 张：

### 3.1 `admin_accounts`
未落地原因与当前替代方案：
- 当前后台管理员直接使用 `users` 表中的 `global_role` 字段区分。
- `SUPER_ADMIN` 与 `TEAM_ADMIN` 已能完成后台登录和接口鉴权。
- 对于单人开发、1 万用户体量场景，这种合并方案维护成本更低。

影响：
- 当前无法对“后台账号”和“前台用户账号”做彻底物理隔离。
- 若后续需要多后台账号体系、独立登录审计、后台专属密码策略，再补独立表更合适。

### 3.2 `audit_logs`
未落地原因与当前替代方案：
- 当前项目已实现接口级异常处理与日志输出，但未将操作审计写入数据库。
- 适合先用文件日志完成轻量审查，再决定是否引入表级审计。

影响：
- 当前无法直接按数据库维度查询“谁在什么时候审核了什么业务”。
- 提现审核、订单状态变化等信息仍可从业务表状态字段中还原部分过程，但不等同完整审计日志。

### 3.3 `supplier_products`
未落地原因与当前替代方案：
- 当前采用统一商品建模：`products.owner_type + products.owner_id` 标识商品归属。
- 供应商商品、自营商品、本地生活服务分别通过归属类型和专区类型区分。

影响：
- 当前模型更轻，减少表数量和同步成本。
- 若后续需要供应商独立商品池、供应商商品审核流、供应商专属价格体系，再拆出 `supplier_products` 更合理。

### 3.4 `asset_transfer_records`
未落地原因与当前替代方案：
- 当前积分转赠已通过 `user_asset_ledgers` 记录资金变动。
- 转赠相关来源可由 `business_type`、`source_id`、`source_no`、`remark` 组合表达。

影响：
- 当前可以查到账变结果，但不如独立转赠表直观。
- 若后续需要严格展示“转出用户、转入用户、审批状态、对冲关系”，建议补独立表。

## 4. 当前 ORM 与 SQL 脚本的一致性

### 4.1 表覆盖一致
- `server/app/models/__init__.py` 已导出全部当前模型。
- `server/sql/schema.sql` 中的建表清单与模型数量一致，均为 `34` 张。
- 当前不存在“SQL 有表但 ORM 没模型”或“ORM 有模型但 SQL 没建表语句”的明显分叉。

### 4.2 枚举与业务口径一致
当前核心枚举已在 `server/app/models/enums.py` 落地，覆盖：
- 全局角色：`SUPER_ADMIN`、`TEAM_ADMIN`、`USER`
- 用户状态：`ENABLED`、`DISABLED`
- 团队角色：`OWNER`、`MEMBER`
- 资产类型：`BALANCE`、`POINTS`、`VOUCHER`、`AI_COUPON`
- 专区类型：`REPURCHASE`、`SELF_OPERATED`、`HOT_SALE`、`LOCAL_LIFE`
- 订单类型：套餐、自营、复购、爆款、本地生活、供应商入场等

说明：
- 规划版文档中的关键枚举已基本被当前模型吸收。
- 当前代码中还扩展了若干运行态枚举，如商品状态、支付状态、提现状态、资格审核状态等。

### 4.3 运行时以 ORM 为主
- 启动文件 `server/app/main.py` 在生命周期内调用 `init_db()`。
- `server/app/db/init_db.py` 通过 ORM 执行 `create_all()`。
- 这意味着当前运行态“真实建表来源”首先是模型定义，其次才是 `schema.sql` 作为人工执行脚本。

## 5. 当前结构与规划版的关键差异

### 5.1 管理员体系未物理拆表
- 规划版：`users` + `admin_accounts`
- 当前实现：仅 `users`

当前评价：
- 更适合单人开发阶段，登录口径简单。
- 但后续若要支持运营账号体系、后台子账号、账号冻结审计，建议补独立后台账户表。

### 5.2 资产转赠未独立建表
- 规划版：`asset_transfer_records`
- 当前实现：并入 `user_asset_ledgers`

当前评价：
- 对当前“积分转赠给上下级”足够。
- 对复杂审批、双边对账、冲正场景还不够细。

### 5.3 供应商商品未独立建表
- 规划版：`supplier_products`
- 当前实现：统一进入 `products`

当前评价：
- 对当前四专区统一商品展示更友好。
- 对未来招商中台、供应商独立后台、供应商批量商品管理功能，扩展空间略受限。

### 5.4 审计能力仍偏轻
- 规划版：`audit_logs`
- 当前实现：应用日志 + 业务状态字段

当前评价：
- 当前适合轻量化上线和内部审查。
- 若业务进入正式运营期，建议将审核、核销、配置修改补充为数据库审计表。

## 6. 当前数据库工程化状态

### 6.1 已具备
- ORM 模型分域清晰，按业务文件拆分
- 命名规范统一，字段口径较稳定
- 启动即建表，适合单机开发调试
- 独立 `schema.sql`，适合 MySQL 手动初始化

### 6.2 当前仍建议补强
- 目前未见独立迁移目录，版本演进仍偏手工
- `schema.sql` 当前未显式声明物理 `FOREIGN KEY` 约束
- 业务强依赖枚举值，后续改枚举时需同步接口与前端

说明：
- ORM 模型中已定义大量逻辑外键引用，例如用户、团队、订单之间的 `ForeignKey`。
- 但 `server/sql/schema.sql` 更偏“轻量初始化脚本”，没有继续下沉为强约束 DDL。
- 这对早期开发更灵活，但对正式生产库治理会弱一些。

---

## 7. 审查结论

- 当前数据库实现已经覆盖 APP 一体化商城的主干交易与业务能力，可以支撑当前后端、后台管理端、移动端 H5 的联调与继续开发。
- 当前与规划版数据库设计的主要差异，集中在 `admin_accounts`、`audit_logs`、`supplier_products`、`asset_transfer_records` 这 4 张表未落地。
- 这 4 张表均属于“治理增强 / 精细化拆分”类型，不影响当前用户注册、团队、返现、资产、四专区商品、订单、本地生活主流程。
- 如下一阶段准备进入正式运营或多管理员协作，建议优先补：`audit_logs`、`asset_transfer_records`、`admin_accounts`。
