# 卓越项目安全审计报告

> 审计日期：2026-08-21  
> 审计类型：源代码、依赖、部署配置及线上只读检查  
> 当前状态：问题已记录，尚未实施修复  
> 适用范围：`server`、`admin-web`、`mobile-uniNew2`、Docker Compose 与部署脚本

## 1. 执行摘要

当前线上版本存在需要立即处置的安全风险，不建议继续以现状长期暴露公网。

本次审计确认两条严重级别为 Critical 的完整攻击链：

1. 公开的 App 免登录接口仅凭手机号签发 JWT，结合系统内固定创建的超级管理员账号，可导致无需凭证取得超级管理员权限。
2. 旧版 uni-h5 的跨源消息桥未校验消息来源，结合任意 URL WebView、可修改的运行时 API 地址和自动附加的 Bearer token，可导致移动端会话令牌被恶意页面窃取。

此外还确认了订单与本地生活业务可绕过真实支付、团队管理员跨团队访问、手机号抢注、验证码无限尝试、敏感字段泄露、生产端口明文暴露、依赖漏洞等多项高风险问题。

本次审计仅进行了只读验证。未调用会签发 token、创建账号、修改订单或改变线上数据的接口，也未尝试使用默认管理员凭据登录。

## 3. 详细发现

### SEC-001：裸手机号登录导致任意账户及超级管理员接管

**严重度：Critical**

**证据：**

- `server/app/api/v1/auth.py:106-121` 的 `POST /api/v1/auth/app-login` 不要求登录、App 签名、共享密钥或上游身份令牌。
- `server/app/schemas/auth.py:52-64` 只校验手机号格式。
- `server/app/services/auth_service.py:115-147` 按手机号查询用户，存在时直接签发 JWT；不存在时自动创建账户。
- `server/app/db/seed.py:27-39` 首次启动时创建固定手机号的超级管理员。
- `server/app/main.py:31-34` 每次应用启动都会执行默认数据初始化。

**线上验证：**

- `https://zyhskj.shop/openapi.json` 中存在该接口。
- OpenAPI operation 没有 `security` 属性。
- 请求模型仅要求 `phone`，其余字段为可选。
- 未实际发送 POST 请求，避免签发凭据或改变线上数据。

**影响：**

攻击者可接管任意已知手机号账户。由于超级管理员手机号固定存在，攻击者无需知道密码即可取得超级管理员 JWT，进而访问用户、订单、资产、提现、权限和系统配置接口。

**建议：**

- 立即在网关或 WAF 封禁该路由。
- 删除裸手机号免登录逻辑，改为服务端校验的一次性短时票据。
- 票据必须绑定手机号、`audience`、时间戳、nonce 和调用方身份，并只能消费一次。
- 停用固定超级管理员，审计历史管理员操作并使现有 JWT 失效。

### SEC-002：uni-h5 跨源消息桥导致 Bearer token 外泄

**严重度：Critical**

**证据：**

- `mobile-uniNew2/subpackages/profile/mini-webview.vue:34-36` 将任意 `query.url` 交给 `<web-view>`。
- `mobile-uniNew2/pages.json:206-209` 注册了可直接访问的 WebView 路由。
- 当前锁定的 `@dcloudio/uni-h5` 为 2023 年版本。
- `mobile-uniNew2/node_modules/@dcloudio/uni-h5/dist/uni-h5.es.js:15664-15709` 全局监听 `message`，只检查消息类型，不检查 `event.origin` 或 `event.source`。
- 同文件 `16597-16604` 根据消息中的名称直接执行 `uni[name](arg)`。
- 同文件 `16631-16648` 创建 iframe，未设置来源白名单或 sandbox。
- `mobile-uniNew2/config/index.js:96-103,161-176` 接受运行时 API 地址，生产环境只拒绝本机地址，不限制受信域名。
- `mobile-uniNew2/api/request.js:45-61` 对当前 API 地址自动附加 `excellent_token`。

**线上验证：**

- `175.27.228.166:8082` 的生产 JavaScript 包含 `WEB_INVOKE_APPSERVICE` 消息桥、运行时 API key 和 WebView 路由。
- 线上 `subpackages-profile-mini-webview` 构建块确认会解码任意 URL 并传给 WebView。

**影响：**

恶意 iframe 或父页面可通过消息桥修改运行时 API 地址并触发页面重载。随后客户端会把现有 Bearer token 发送到攻击者控制的 HTTPS 主机，导致用户会话被接管。

**建议：**

- 立即禁用任意 URL WebView。
- 生产构建固定 API 为同源 HTTPS，删除运行时 setter。
- 升级整套 DCloud/UniApp 依赖，不能只单独替换一个包。
- 消息处理必须同时校验 `event.origin`、`event.source` 和允许调用的 API 名单。
- iframe 使用严格 sandbox，并配置 CSP `frame-src`、`connect-src` 和 `frame-ancestors`。

### SEC-003：后台可无支付凭证将订单标记为已付

**严重度：High**

**证据：**

- `server/app/api/v1/orders.py:211-218` 允许 SUPER_ADMIN 或 TEAM_ADMIN 调用 `/admin/orders/{id}/pay`。
- `server/app/services/admin_permission_service.py:286-287` 将该请求归入默认授予团队管理员的 `orders:manage`。
- `server/app/services/order_service.py:330-334` 不检查支付交易或线下收款凭证，直接调用 `_mark_paid`。
- `server/app/services/order_service.py:880-916` 将订单置为已付，同时发放套餐权益、冻结佣金，并可能立即结算佣金和区域分红。

**影响：**

恶意或被盗的团队管理员账户可给同团队串谋账户制造免费已付订单及可提现收益。

**建议：**

- 移除通用手工标记付款功能。
- 如业务必须支持线下收款，应限制为独立权限、双人复核，并绑定不可重复的收款流水。
- 权益和佣金只能由已验签支付回调或经过对账的支付记录触发。

### SEC-004：本地生活核销权限错误并可结算未付款订单

**严重度：High**

**证据：**

- `server/app/services/admin_permission_service.py:294-299` 将所有 `/admin/local-life` POST 请求映射为 `local-life:create`。
- `server/app/api/v1/local_life.py:225-231` 的订单核销接口因此不要求已定义的 `local-life:verify` 权限。
- `server/app/services/local_life_service.py:436-463` 在核销未付款订单时直接将其设为 PAID/COMPLETED，并冻结、结算佣金。

**影响：**

只有“创建本地生活”权限、没有“核销”权限的团队管理员，也可以将未付款订单核销为已支付并触发资金收益。

**建议：**

- 为核销路由设置显式的 `local-life:verify` 权限依赖。
- 核销不能代替支付确认。
- 线下现金场景应建立单独的支付凭证、账务流水和复核流程。

### SEC-005：公开注册允许手机号预注册和身份抢占

**严重度：High**

**证据：**

- `server/app/api/v1/auth.py:25-28` 的注册接口不验证短信码或手机号所有权。
- `server/app/services/auth_service.py:162-170` 创建任意未注册手机号的账户并立即签发 JWT。
- `server/app/services/auth_service.py:173-183` 密码登录不检查 `is_phone_verified`。
- `server/app/api/deps/auth.py:16-28` 也不检查手机号验证状态。

**影响：**

攻击者可提前使用受害者手机号注册、建立邀请关系、创建资产或订单，并持续使用已签发 JWT。真实用户后续注册会被拒绝。

**建议：**

- 注册必须消费服务端生成的一次性 OTP 凭证。
- 未验证手机号的账户不得登录或使用业务功能。
- 重置密码和手机号找回后应撤销该用户全部历史会话。

### SEC-006：固定超级管理员账号及默认密码

**严重度：High**

**证据：**

- `server/app/db/seed.py:27-39` 在首次启动时创建固定手机号、固定密码的超级管理员。
- 没有强制首次改密或 MFA 流程。

**影响：**

即使关闭 SEC-001 的免登录接口，任何仍使用默认密码的部署都可能被直接登录。

**建议：**

- 删除源码中的固定账号和密码。
- 首次部署使用一次性随机凭据，通过安全渠道交付，并强制首次改密。
- 管理员登录启用 MFA。

### SEC-007：登录与验证码缺少抗爆破机制

**严重度：High**

**证据：**

- `server/app/services/auth_service.py:186-240` 只按手机号设置 60 秒短信发送冷却，无 IP、设备或全局限制。
- `server/app/services/auth_service.py:243-267` 对 6 位验证码没有失败次数上限。
- `server/app/services/auth_service.py:158-159` 使用非密码学安全的 `random.choices` 生成验证码。
- 密码登录和管理员登录同样没有失败计数、锁定、渐进延迟或 MFA。

**影响：**

攻击者可进行验证码爆破、密码撞库、管理员密码猜测和短信轰炸。

**建议：**

- 使用 `secrets` 生成 OTP。
- 使用 Redis Lua 或事务实现原子化尝试计数。
- 同时按 IP、设备、手机号和账号实施限流，并增加验证码尝试上限。
- 管理员启用 MFA、异常登录通知和风险控制。

### SEC-008：团队管理员多处绕过团队数据范围

**严重度：High**

**确认位置：**

- `server/app/api/v1/admin_invites.py:52-225`：团队管理员可查询全站用户手机号和邀请关系。
- `server/app/api/v1/payments.py:60-108`：可查询全站支付流水及 provider、request、notify 原始载荷。
- `server/app/api/v1/admin_commerce.py:36-251`：可跨团队查看或删除收藏、足迹，并查看全站物流订单。
- `server/app/api/v1/users.py:144-152`：更新用户状态时丢弃当前管理员对象。
- `server/app/services/user_service.py:442-447`：可按任意 `user_id` 修改状态，未验证团队范围。

**影响：**

团队管理员可读取跨团队个人信息和交易数据，部分接口还可修改其他团队用户甚至管理员状态。

**建议：**

- 所有管理查询统一从 `AdminScopeService` 生成基础查询。
- 写操作在读取目标对象后再次执行范围校验。
- 增加针对同团队、跨团队、无团队、ALL scope 的集成测试。

### SEC-009：生产容器端口通过 HTTP 公网暴露

**严重度：High**

**证据：**

- `docker-compose.prod.yml:129-130` 发布 `8000:8000`。
- `docker-compose.prod.yml:148-149` 发布 `8081:80`。
- `docker-compose.prod.yml:161-162` 发布 `8082:80`。
- `deploy.sh` 仍输出公网 HTTP API 地址。

**线上验证：**

- `175.27.228.166:8000` 可访问 Uvicorn API、Swagger 和 OpenAPI。
- `175.27.228.166:8081` 可访问管理端。
- `175.27.228.166:8082` 可访问移动 H5。
- 三个入口均允许绕过域名 HTTPS 和外层反向代理。

**影响：**

用户若访问直连地址，密码、管理员凭据和 Bearer token 可通过明文 HTTP 传输；外层 WAF、限流和安全头也会被绕过。

**建议：**

- 安全组立即关闭公网 `8000`、`8081`、`8082`。
- 宿主机反代场景绑定为 `127.0.0.1:端口:容器端口`。
- 容器反代场景删除 `ports`，只在内部网络使用 `expose`。

### SEC-010：生产 App 可将 token 发往明文开发 API

**严重度：High**

**证据：**

- `mobile-uniNew2/subpackages/profile/settings.vue:33-63,114-186` 在生产 UI 中显示环境切换，并包含硬编码 HTTP 开发主机。
- 切换环境时不清除现有登录状态。
- `mobile-uniNew2/api/request.js:45-61` 对切换后的 API 地址继续附加 Bearer token。
- `mobile-uniNew2/manifest.json:25` 允许 Android 明文流量。
- 配置的旧开发 API 当前仍通过 HTTP 响应。

**影响：**

用户误操作、社工诱导或同网中间人攻击可导致生产 token 被发送到旧开发服务，生产数据也可能写入开发环境。

**建议：**

- 生产构建完全移除环境切换 UI 和 setter。
- 固定 HTTPS 主机白名单。
- 环境发生变化时必须先清除 token 和用户缓存。
- Android 设置 `usesCleartextTraffic=false`。

### SEC-011：API 响应泄露密码字段

**严重度：Medium**

**证据：**

- `server/app/api/v1/auth.py:25-45` 的注册、密码登录和验证码登录直接返回 SQLAlchemy `User` 实例。
- `server/app/api/v1/users.py:28-35,144-152` 的资料更新和状态更新也返回原始对象。
- `server/app/models/user.py:15` 的对象包含 `password_hash`。
- 本地只读编码验证确认 FastAPI 会将该字段放入 JSON。
- `server/app/services/user_service.py:299-312` 返回 legacy profile 的所有数据库列。
- `server/app/models/user.py:60-61` 的 legacy profile 包含 `password` 和 `pay_password`。

**影响：**

客户端、团队管理员或日志系统可能获得密码哈希、历史密码字段或支付密码字段，进而进行离线破解和凭据复用攻击。

**建议：**

- 所有 API 使用显式响应 DTO 或字段白名单序列化器。
- 禁止直接序列化 ORM 实体。
- 从 legacy API 和数据库迁移中移除不再需要的密码字段。

### SEC-012：微信支付回调验证存在绕过路径

**严重度：条件性 High**

**证据：**

- `server/app/api/v1/payments.py:45-49` 未向服务层传递 `Wechatpay-*` 平台签名请求头。
- `server/app/services/payment_service.py:702-705` 在 payload 没有 `resource` 时直接返回原始 JSON。
- `server/app/services/payment_service.py:777-841` 随后可依据 `out_trade_no` 和成功状态标记 WECHAT 交易支付，未验证金额、商户号或应用 ID。

**利用条件：**

当前普通下单流程明确禁用微信支付，因此只有数据库中存在历史或其他路径创建的 WECHAT 待支付交易时才能利用。

**建议：**

- 强制要求加密 `resource`。
- 验证微信平台签名、时间戳、nonce 和证书序列号。
- 校验 `mchid`、`appid`、金额、币种和订单号。
- 对回调事件建立防重放记录。

### SEC-013：依赖包含已知漏洞

**严重度：High/Medium**

**后端：**

- `server/requirements.txt:1` 固定 `fastapi==0.115.0`，当前解析到 `starlette==0.38.6`。
- `server/requirements.txt:13` 固定 `python-multipart==0.0.12`。
- 两者包含多项 multipart CPU、内存、临时文件耗尽和参数解析漏洞。
- 项目存在真实 multipart 上传入口，公网 `8000` 又绕过 Nginx 请求体限制。
- `python-jose==3.3.0`、`cryptography==46.0.7`、`orjson==3.10.7` 也命中当前漏洞数据库记录，但部分漏洞与当前调用方式不直接匹配。

**前端：**

- 管理端 `npm audit --omit=dev`：4 high、1 moderate。
- 管理端实际安装 `axios==1.14.0`，当前审计建议升级到已修复版本。
- 移动端审计：24 high、9 moderate、1 low。
- 移动端多数告警属于 UniApp 构建链或开发服务器，但旧 uni-h5 消息桥问题在本项目中已确认可达。

**建议：**

- 升级 FastAPI 到支持已修复 Starlette 的兼容版本。
- `python-multipart` 至少升级到 `0.0.31`，并回归上传、导入、支付回调流程。
- UniApp/DCloud 依赖按整套兼容版本升级。
- 不要直接运行破坏性的 `npm audit fix --force`。

### SEC-014：普通用户可给任意供应商添加有效协议

**严重度：Medium**

**证据：**

- `server/app/api/v1/suppliers.py:31-39` 只要求用户登录，不把当前用户传给服务层。
- `server/app/services/supplier_service.py:132-146` 不验证供应商归属。
- `server/app/models/supplier.py:41-50` 的新协议默认有效。

**影响：**

普通用户可向其他用户的供应商记录添加伪造协议，并影响商品资格判断。

**建议：**

- 校验 `supplier.user_id == current_user.id`。
- 协议默认状态应为待审核，由独立审核流程激活。

### SEC-015：JWT 无撤销能力且复用银行卡加密密钥

**严重度：Medium**

**证据：**

- `server/app/core/security.py:21-27` 的 JWT 只有 `sub`、角色和 `exp`，默认有效期 24 小时。
- 没有 `jti`、会话版本、吊销列表或 refresh token 轮换。
- 改密和退出登录不会使历史 JWT 失效。
- `server/app/utils/sensitive_data.py:10-23` 使用同一 `SECRET_KEY` 派生 Fernet 密钥加密银行卡号。

**影响：**

被盗 token 在到期前持续有效；直接轮换 `SECRET_KEY` 虽能使 JWT 失效，却会导致历史银行卡和提现卡号无法解密。

**修复注意：**

不能直接修改现有 `SECRET_KEY` 后重启。应按以下顺序处理：

1. 引入独立 `JWT_SIGNING_KEY`。
2. 引入版本化 `DATA_ENCRYPTION_KEY`，初始值保持与当前数据兼容。
3. 支持旧数据密钥只读解密，并批量重加密到新版本。
4. 验证历史银行卡和提现数据均可解密。
5. 轮换 JWT 签名密钥，使历史 token 失效。
6. 迁移完成后安全归档或销毁旧数据密钥。

### SEC-016：基础设施密码偏短且复用

**严重度：Medium**

**证据：**

- 当前根 `.env` 中 MySQL root、MySQL 应用用户和 Redis 密码均为 8 位。
- 三者使用相同值。
- 本报告未读取或记录密码内容。

**影响：**

服务或容器被攻破后，凭据复用会扩大横向移动和数据库提权影响。

**建议：**

- 分别生成至少 24 至 32 位随机密码。
- MySQL root、应用用户和 Redis 禁止复用。
- 使用云密钥管理或 Docker secrets，避免长期放在普通环境文件中。

### SEC-017：缺少浏览器安全头且生产文档公开

**严重度：Medium**

**证据：**

- `admin-web/nginx.conf` 和 `mobile-uniNew2/nginx.conf` 未设置 CSP、`frame-ancestors`/`X-Frame-Options`、`X-Content-Type-Options`、`Referrer-Policy` 或 `Permissions-Policy`。
- 线上管理站只观察到 HSTS。
- 线上 `/docs` 和 `/openapi.json` 可公开访问。
- 管理端 token 长期存储于 `localStorage`。

**建议：**

- 管理端至少使用 `frame-ancestors 'none'`、`X-Content-Type-Options: nosniff` 和严格 CSP。
- 为移动 H5 限制 `connect-src` 与 `frame-src`。
- 生产关闭或限制 Swagger/OpenAPI 到管理网络。
- 评估改用 HttpOnly、Secure、SameSite Cookie、短会话和 CSRF 防护。

### SEC-018：镜像、构建和容器隔离不足

**严重度：Medium**

**证据：**

- `docker-compose.prod.yml` 使用 `server-latest`、`admin-web-latest`、`mobile-uniNew2-latest` 可变标签。
- 部署脚本每次直接拉取这些标签。
- 基础镜像没有固定 digest。
- 两个前端 Dockerfile 使用 `npm install` 而非 `npm ci`。
- Python 仅固定直接依赖，没有 transitive lock 和 hash。
- MySQL、Redis、API 和两个前端共用一个 Docker 网络。
- Compose 未设置 `read_only`、`cap_drop`、`no-new-privileges` 和资源上限。

**建议：**

- 使用不可变版本标签与 `@sha256` digest。
- 建立镜像签名、SBOM 和漏洞扫描流程。
- 使用 `npm ci`，Python 使用带 hash 的锁文件。
- 拆分 edge/data 网络，将数据库网络设为 internal。
- 为容器增加只读文件系统、最小 capabilities 和 CPU/内存限制。

## 4. 建议处置顺序

### P0：立即止血

1. 网关封禁 `POST /api/v1/auth/app-login`。

3. 停用固定超级管理员并强制管理员改密。
4. 禁用任意 URL WebView、生产环境切换和运行时 API setter。

6. 审计近期管理员登录、权限变更、用户状态、订单支付、佣金、提现和供应商协议记录。
7. 按 SEC-015 的密钥拆分方案使历史 JWT 失效，禁止直接覆盖现有 `SECRET_KEY`。

### P1：优先修复

1. 重构 App 免登录为服务端验证的一次性票据。

5. 所有 API 改为显式响应 DTO，清理 legacy 密码字段。
6. 完整验证微信支付回调。

### P2：持续加固
